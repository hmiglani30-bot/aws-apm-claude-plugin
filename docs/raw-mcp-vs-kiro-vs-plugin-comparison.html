Architectural comparison

Raw MCP  vs  Kiro Power  vs  CW Plugin

Three ways to use the same four AWS observability MCP servers — bare-bones, Kiro IDE with steering files, or the Claude Code plugin with slash commands and HTML artifacts. Same backends, very different operator experiences.

Just the servers. No orchestration, no presentation.

How each layer is built

All three sit on top of the same four awslabs MCP servers. The differences are everything around them.

Layer Raw MCP Kiro Power CW Plugin
Platform Any MCP-capable client Kiro IDE only Claude Code / Cowork
MCP servers Same 4 across all three: cloudwatch, application-signals, cloudtrail, aws-documentation.
Orchestration layer None  User stitches tool calls. POWER.md router  Routes to one of 8 scenario steering files. 10 slash commands + 16 skills  Typed, named workflows.
Context loading None — every turn starts cold. Dynamic — POWER.md loads only the relevant steering file (~200–700 lines). Dynamic — slash command pulls only its skill + artifact template.
Presentation layer None  Raw JSON tool results. Text-only  Markdown narration in chat. HTML artifacts  6 interactive templates (health card, breach explainer, waterfall, etc.).
Version pinning User pins manually. Pinned in Kiro config. Pinned in plugin mcp.json.
State / memory None None — each session is independent. Incident memory  JSON under .aws-apm/incidents/; surfaces recurrences.
Safety model Server-level read/write tool tags. Implicit — read-only steering files, no write actions documented. Explicit  ACTION-SAFETY-MODEL.md defines read-only vs. confirmed-write per tool.

What only one side has

The non-overlapping bits — where each project bets differently.

Only in Kiro Power 8 steering files · 3,712 lines

Broader scope: design, audit, and gap-analysis workflows that the plugin doesn't touch.

  • Codebase gap analysis Reads source, identifies missing logs/metrics/traces, recommends instrumentation. observability-gap-analysis.md (430 lines).
  • Proactive alerting design Designs new CloudWatch alarms from scratch — thresholds, SNS wiring, composite alarms. alerting-setup.md (501 lines).
  • CloudTrail data-source decision tree Picks Lake vs. Lookup vs. S3+Athena based on time range, cost, and query shape. cloudtrail-data-source-selection.md (313 lines).
  • Standalone log analysis A first-class workflow — not just a step inside an incident. log-analysis.md (269 lines).
  • Security & compliance auditing CloudTrail-driven audit runbook for IAM, S3, KMS, network changes. security-auditing.md (730 lines).
  • Application Signals onboarding End-to-end setup walkthrough, not just verification. application-signals-setup.md (217 lines).

Only in CW Plugin 10 commands · 16 skills · 6 artifacts

Deeper investigation UX: typed workflows, persistent memory, and developer-grade output.

  • Interactive HTML artifacts Service Health Card, SLO Breach Explainer, Trace Waterfall, Top Suspected Cause, SLO Report, Copy-to-Incident — fixed visual grammar across investigations.
  • Incident memory Persists every investigation as JSON under .aws-apm/incidents/. Surfaces "we saw this before" before re-investigating.
  • Trace-to-code mapping Span annotations → file/method → recent commits. Bridges production telemetry to the code that needs the fix.
  • Investigation validator Self-check pass before output: metadata footer, evidence citations, deep links, ruled-out hypotheses, burn-rate math, confidence levels.
  • Service ownership resolution AWS tags + Service Catalog + CODEOWNERS + GitHub teams + PagerDuty + Slack channel → "Likely owner" + "Suggested page".
  • Explicit safety model ACTION-SAFETY-MODEL.md classifies every MCP tool as read-only vs. confirmed-write. Kiro relies on convention.
  • Slash-command UX /cw-alarm-response, /cw-investigate-slo, /cw-investigate-latency, /cw-doctor, /cw-slo-report, etc. — discoverable, autocompleted, scoped.

Bottom line

All three sit on the same four MCP servers. The split is what's built on top.

Kiro Power is broader — codebase gap analysis, alerting design, security auditing, App Signals onboarding, and a standalone log-analysis workflow. It's the right tool when the question is "what should we be monitoring?" or "is this set up correctly?"

CW Plugin is deeper on investigation UX and developer workflow — slash-commanded, artifact-rendered, validated, with persistent incident memory and trace-to-code mapping. It's the right tool when the question is "what just broke and what do I tell the incident channel?"

They're complementary, not competitive. The MCP servers are shared infrastructure; the value lives in the orchestration and presentation layers each project builds — and those layers target different parts of the operator's day.
